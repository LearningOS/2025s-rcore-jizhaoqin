## 实现功能总结

```rust
pub fn sys_get_time(ts: *mut TimeVal, _tz: usize) -> isize
```
- 问题: `ts`为用户空间虚拟地址, 不能直接从内核态进行访问
- 解决: 根据当前用户的`token`(`satp`)使用`translated_byte_buffer()`间接访问(这里认为这里ts不需要检查)

```rust
pub fn sys_trace(trace_request: usize, id: usize, data: usize) -> isize
```
- 问题: `id`作为用户空间虚拟地址传入时, 不能直接从内核态访问
- 解决: 在内核空间使用`get_page_table_entry()`查询此虚拟地址是否属于用户态, 且是否可读/写, 若满足再使用`translated_byte_buffer()`间接访问

```rust
pub fn sys_mmap(start: usize, len: usize, prot: usize) -> isize
```
- 实现: 执行要求的各种检查, 使用`insert_framed_area()`分配物理页帧, 完成地址映射并设置权限

```rust
pub fn sys_munmap(start: usize, len: usize) -> isize 
```
- 实现: 执行检查, 使用`TASK_MANAGER.inner.task.MemorySet.munmap()`移除维护的页帧及其映射

## 问答作业

#### 1. 请列举 SV39 页表页表项的组成，描述其中的标志位有何作用？

- 标识位: [0, 7]
- 0: V, 此页表项是否有效
- 1: R, 是否可读
- 2: W, 是否可写
- 3: X, 是否可执行
- 4: U, 是否用户态可访问
- 5: G, 是否为全局(多地址空间共享)页
- 6: A, 是否被访问过
- 7: D, 是否被写过
- [8, 9] & [54, 63]: 保留位
- [10, 53]: 44位物理页号 ,

#### 2. 缺页

- 请问哪些异常可能是缺页导致的？

| 异常类型                     | 异常编号 | 触发条件（典型缺页原因）                                          |
| ------------------------ | ---- | ----------------------------------------------------- |
| `Instruction Page Fault` | `12` | CPU取指时，地址无效、页表项不存在、页表项的权限不允许执行（X=0）、或V=0          |
| `Load Page Fault`        | `13` | 加载指令(如 `lw`、`ld`)访问的虚拟地址无效、页表项无效（V=0）、或R=0    |
| `Store/AMO Page Fault`   | `15` | 写入或原子操作(如 `sw`、`amoswap.w`)访问的地址无效、页表项无效、或W=0 |

- 发生缺页时，描述相关重要寄存器的值，上次实验描述过的可以简略
  - `scause`: 陷入原因寄存器, 描述导致 trap 的具体异常类型（缺页异常编号为 12、13、15）
  - `stval`: 异常相关值寄存器, 通常保存访问失败的虚拟地址(faulting virtual address), 操作系统可以根据该地址尝试补页或终止进程
  - `sstatus`: 特权级状态寄存器, 提供 trap 前的上下文信息，如用户态/内核态、使能位等, 可用来判断当前是否为用户态引发的访问, 或是否因权限限制引发
  - `satp`: 页表基址寄存器, 控制地址转换模式与页表根地址（根页表物理地址）
  - `sepc`: 异常程序计数器, 保存触发异常的指令地址(即下一次将要执行的指令地址)

- 缺页有两个常见的原因，其一是 Lazy 策略，也就是直到内存页面被访问才实际进行页表操作。 比如，一个程序被执行时，进程的代码段理论上需要从磁盘加载到内存。但是 os 并不会马上这样做， 而是会保存 .text 段在磁盘的位置信息，在这些代码第一次被执行时才完成从磁盘的加载操作。
- 这样做有哪些好处？
  - 节省内存资源: 程序可能定义了很多代码段、数据段、堆、栈，但并非所有部分都会被访问
  - 提高程序启动速度: 启动时只进行最小的初始化，真正需要的页面在访问时再加载
  - 可支持更高级的内存管理技术
- 处理 10G 连续的内存页面，对应的 SV39 页表大致占用多少内存 (估算数量级即可)？
  - 三级页表, 每级的每个页表都有512个条目, 每个条目能管理4KB内存(offset为位), 所以每个页表能管理2MB内存, 每个页表本身也是4KB大小, 由上级页表的一个条目管理
  - 所以10GB虚拟内存, 需要10GB/2MB = 5120 张1级页表, 5120/512 = 10 张2级页表, 1张3级页表, 共5000张表, 额外占用约20MB内存.
- 请简单思考如何才能实现 Lazy 策略，缺页时又如何处理？描述合理即可，不需要考虑实现
  - 初始化页表时不立即映射物理页
  - 为这些延迟页面保留元信息
  - CPU访问未映射的懒加载虚拟地址页时, 触发页异常，陷入内核
  - 如果地址合法则分配一个空闲物理页, 并设置对应页表项
  - 更新 TLB缓冲区
  - 恢复用户态
- 缺页的另一个常见原因是 swap 策略，也就是内存页面可能被换到磁盘上了，导致对应页面失效。此时页面失效如何表现在页表项(PTE)上？

| V | R/W/X | PPN            | 含义          |
| - | ----- | -------------- | ----------- |
| 0 | X（无效） | 编码后的 swap slot | 此页不在内存，已被换出 |


#### 3. 双页表与单页表

- 为了防范侧信道攻击，我们的 os 使用了双页表。但是传统的设计一直是单页表的，也就是说， 用户线程和对应的内核线程共用同一张页表，只不过内核对应的地址只允许在内核态访问。 (备注：这里的单/双的说法仅为自创的通俗说法，并无这个名词概念，详情见 KPTI )
- 在单页表情况下，如何更换页表？
  - 操作系统必须显式更新硬件中指向页表的寄存器`satp`并执行`sfence.vma`更新`TLB`, 其写入会立即改变页表根目录，进而改变整个虚拟地址映射
- 单页表情况下，如何控制用户态无法访问内核页面?
  - 设置标志位`U=0`
- 单页表有何优势？
  - 上下文切换开销更小
  - 内核访问用户地址更方便
  - 实现更简单
- 双页表实现下，何时需要更换页表？
  - 从用户态进入内核态时(中断 / 系统调用 / 异常)
  - 从内核态返回用户态时
- 假设你写一个单页表操作系统，你会选择何时更换页表（回答合理即可）？
