## 问答作业

#### 1. 在我们的多线程实现中，当主线程 (即 0 号线程) 退出时，视为整个进程退出， 此时需要结束该进程管理的所有线程并回收其资源。 

- 需要回收的资源有哪些？

  - 主线程退出代表整个进程退出，此时需要回收的资源包括：

    | 资源类型                         | 说明                               |
    | ---------------------------- | -------------------------------- |
    | **所有线程的内核栈**                 | 每个线程有独立的内核栈，必须释放其页表映射或物理内存块。     |
    | **所有线程的用户栈**                 | 通常也是一段虚拟内存，需从地址空间中移除并释放物理页。      |
    | **所有 TaskControlBlock（TCB）** | 每个线程的调度控制结构体，需从调度队列等结构中移除并释放。    |
    | **地址空间（PageTable）**          | 多线程共享同一个地址空间，主线程退出时，整个地址空间会销毁。   |
    | **打开的文件描述符等资源**              | 若线程间共享 fd table，退出时需要关闭所有未关闭的文件。 |
    | **资源引用计数（Arc、Rc）**           | 若资源通过 `Arc<T>` 管理，需要检查引用是否归零再回收。 |

- 其他线程的 TaskControlBlock 可能在哪些位置被引用，分别是否需要回收，为什么？
  - 如下表

    | 可能的引用位置      | 是否需要回收 | 原因解释                 |
    | --------------- | ------ | -------------------- |
    | 调度队列            | ✅ 是    | 否则线程仍会被调度，造成死引用或错误行为 |
    | 被其他线程持有（join 等） | ✅ 是    | 否则主线程退出后这些引用无法释放     |
    | 睡眠队列/等待队列       | ✅ 是    | 会导致资源泄漏或逻辑错误（唤醒无效线程） |
    | 内核资源（管道、信号量）中   | ✅ 是    | 保证内核结构清洁，避免野指针或双重唤醒  |

#### 2. 对比以下两种 Mutex 中的实现，二者有什么区别？这些区别可能会导致什么问题？

- 两者应该是等价的, 主要区别在于, Mutex1每个task在其临界区域的开头和结尾都会lock和unlock, 而Mutex2只会在第一个task临界区域的开始lock, 在wait_queue最后一个task的临界区域unlock
- Mutex1: [lock -- task1 -- unlock] -- [lock -- task2 -- unlock ] -- ... -- [lock -- taskn -- unlock]
- Mutex2: [lock -- task1 -- ] -- [-- task2 --] -- ... -- [-- taskn -- unlock]
- 在内核代码中两者都能通过测试
  - 但由于Mutex1的等待队列中每一个task在其临界区域的末尾候都会解锁, 可能会导致其他未在队列中的task成功加锁占据资源, 有可能导致此锁资源的等待队列进入饥饿状态
  - 而Mutex2只会被队尾的task解锁, 即整个等待队列全部执行完毕前一直占据锁资源, 队列外不可获取锁资源, 也就能够保证等待队列中的任务按期望的顺序运行直至结束.
